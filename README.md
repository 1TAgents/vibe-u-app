# vibeUapp

一句话需求 → 一支 AI 团队把它做成能用的应用。

区别不在「能生成代码」，而在**每一步都要外部证据才算数**：能不能编译、用例过没过、页面上到底有什么，全部由平台判定，不由模型自述。

---

## 核心主张

> **Agent 产出的是主张，平台产出的是事实。「完成」只能由事实认定。**

整套架构由这一条推出来——角色的边界、工具怎么分、质量门为什么长在那个位置、预算为什么不能由调度器自己改。

## 团队

| 名字 | 角色 | 决定什么 |
|---|---|---|
| **Piper** | 项目 · 调度 | 谁来做、卡在哪了、要不要找人 |
| **Ida** | 产品 | 做什么、优先级、能不能交付 |
| **Luna** | 设计 | 长什么样、给谁用 |
| **Archie** | 架构 | 数据怎么组织、页面怎么分 |
| **Cody** | 实现 | 代码怎么写 |
| **Tess** | 质量 | 怎么验、验什么 |

**流程不写死在代码里。** Piper 每轮看着当前状态决定下一步派给谁——测试挂了归哪一层、老板中途改需求该谁接，都是它的现场判断，不是预设的分支。

## 四道质量门

由**产出了什么**触发，不由流程走到哪触发：

| 门 | 判据 |
|---|---|
| 构建 | 服务端真实编译 |
| 静态审计 | 源码里有没有注定出问题的写法 |
| 功能验收 | 用例在真实 DOM 上跑一遍 |
| 交付验收 | 客观证据（色板、DOM 结构、可访问性缺陷）+ 判断 |

门不能被跳过——subagent 无权关它，调度器也无权关它。

完整设计见 **[docs/architecture.md](docs/architecture.md)**。
