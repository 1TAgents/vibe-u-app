# UI 评审、快照与版本演进方案

> 状态：未来方案，当前不实现。
>
> 当前决策：从面向普通使用者的界面移除“回放 / 重播”入口；保留事件流、历史事件 API、状态折叠和只读回放实现，作为未来快照、版本分支及审计能力的技术基础。项目卡原“回放”位置改为复制应用自身的公开链接。

## 一、背景与决策

项目现在已经有团队群聊。角色结论、失败原因、测试结果和人工修改都能沿同一条时间线阅读，播放式回放与群聊的用户价值高度重叠，而且容易被误解为“可以回滚到这一帧”。

真正需要补齐的不是播放动画，而是两类正式评审和一套可恢复的版本机制：

1. **需求评审**：确认做什么、给谁用、验收边界和本版本不做什么。
2. **UI 评审**：在工程实现前确认页面构图、视觉语言、关键交互和响应式策略。
3. **快照与版本**：能够预览历史状态、重新采用旧版本，或从旧状态创建新的开发分支。

事件日志依然重要。它是刷新恢复、服务端续跑、故障定位和未来审计的事实来源。因此当前只收起可见入口，不删除 `/r/[runId]`、事件 API、事件表或状态折叠逻辑。

## 二、目标工作流

```text
老板提出需求
  → Ida · 产品负责人整理 PRD
  → [需求评审，可配置]
  → Luna · 产品设计师产出可视化 UI 方案
  → [UI 评审，未来新增]
  → Archie · 系统架构师评估技术结构（仅在需要时）
  → Cody · 工程师实现
  → Tess · 质量工程师验收
  → Ida · 产品负责人交付验收
  → 形成可发布版本快照
```

### 需求评审

- 当前已有开关，默认关闭。
- 开启后，PRD 完成即暂停；用户可批准、修改或退回。
- 评审结论必须进入事件流，并成为下游角色唯一有效的需求输入。

### UI 评审

- 与需求评审独立配置，不能用文字版设计说明代替。
- Luna 完成可视化设计产物后暂停，等待用户批准、标注意见或选择其他方案。
- 未通过 UI 评审时，不进入正式工程实现；纯后端或无视觉界面的任务可以由 Piper 判断跳过。
- UI 修改只影响视觉与交互时，默认路由为 Luna → Cody → Tess；涉及数据模型或页面结构时再经过 Archie。

## 三、未来核心概念

| 概念 | 含义 |
|---|---|
| 项目 Project | 一个持续演进的产品，包含所有对话、分支和版本 |
| 分支 Branch | 从某个快照开始的一条后续开发路线 |
| 快照 Snapshot | 某个里程碑上不可变的完整产品状态 |
| 发布 Release | 当前对外生效的稳定快照指针 |
| 设计产物 Design Artifact | Figma 文件、Frame、导出图、设计 Token 和交互说明 |

“回退”在用户界面上是一个简单动作，但底层不应删除或改写原历史。技术动作应是：

- **重新使用此版本**：将发布指针切换到已有稳定快照，不调用模型。
- **从此版本继续**：从该快照创建新分支和新聊天上下文，原分支完整保留。

示例：V1 的 UI 已交付；用户要求修改后得到 V2，随后发现 V1 更好。用户既可以直接重新发布 V1，也可以从 V1 创建 V3，继续提出新的修改要求。V2 仍然保留，便于比较和审计。

## 四、快照内容

快照应在重要里程碑自动生成，也允许人工命名保存。建议包含：

- 父快照、所属分支、创建原因和事件序号。
- 当时有效的 PRD、架构方案、设计方案与验收标准。
- 完整源代码文件树及内容校验值。
- 已编译且可直接运行的 JS/CSS bundle。
- QA 计划、执行结果、浏览器验证结果和已知问题。
- 依赖版本、构建器版本和数据 Schema 版本。
- 页面截图、版本缩略图和视觉差异摘要。
- 未来的 Figma 文件 ID、页面 ID、Frame/组件节点 ID 和外部版本 ID。
- 给后续角色使用的决策摘要，不把全部历史事件重新塞进模型上下文。

不能只依靠事件重新构建历史版本。构建器和依赖会升级，同一份旧代码未来可能得到不同产物；正式快照必须保存不可变源码和当时的已编译 bundle。

## 五、版本操作

未来版本页面建议提供：

1. **预览**：查看该版本真实应用，而不是只看聊天状态。
2. **对比**：比较页面截图、设计 Token、源码、测试和数据 Schema。
3. **从这里继续**：创建新分支，恢复该快照的产物与决策上下文后开始新聊天。
4. **设为当前版本**：在安全检查通过后更新工作区当前指针。
5. **发布此版本**：把稳定公开链接切换到选定快照。
6. **命名与备注**：例如“初版深蓝 UI”“老板确认版”“表格密度调整前”。

代码版本回退和业务数据回退必须分开。默认只切换代码、设计和配置，不回滚用户数据；涉及 Schema 变化时必须先检查兼容性或提供迁移方案。

## 六、Luna 的可视化设计工具

当前 Luna 主要输出结构化文字设计说明，未来应接入 Figma 或同类设计工具，使设计评审发生在编码之前。

Luna 的标准设计产物建议包括：

- 可打开和评论的 Figma 文件或指定 Frame。
- 桌面端与移动端关键页面。
- 组件状态：默认、悬停、禁用、错误、空状态和加载状态。
- 可复用的颜色、字体、间距、圆角和阴影 Token。
- 页面跳转与关键交互原型。
- PNG/SVG 导出预览和平台内缩略图。
- 设计说明及与 PRD 验收项的对应关系。

Figma 不应成为唯一真相源。平台仍需保存导出图、结构化 Token、节点引用和设计摘要；即使外部授权失效，历史版本仍应可识别、可比较。

工程师消费的也不应只有截图。Cody 应同时得到已批准的 Frame、设计 Token、组件状态和交互说明；Tess 的视觉验收应引用同一个已批准设计版本。

## 七、建议的数据结构

未来可新增独立的版本表，而不是继续覆盖 `app_bundles` 当前记录：

```text
project_snapshots
  id
  run_id / project_id
  branch_id
  parent_snapshot_id
  event_seq
  kind                 # requirement / design / build / release
  label
  source_files
  compiled_bundle
  prd
  architecture
  design_artifacts
  qa_report
  build_metadata
  created_at

project_branches
  id
  project_id
  base_snapshot_id
  head_snapshot_id
  created_at

project_releases
  project_id
  snapshot_id
  published_at
```

事件流继续记录谁在何时创建、批准、切换或发布了快照；快照表负责稳定保存可恢复的物化状态。

## 八、分阶段实施

### 阶段 1：版本基础

- 每次成功构建和交付后保存不可变源码与 bundle。
- 增加版本列表、缩略图、预览和命名。
- 公开应用链接改为读取发布版本指针。

### 阶段 2：恢复与分支

- 支持“从此版本继续”。
- 新分支只继承目标快照之前的有效上下文。
- 支持把历史稳定版本重新设为当前版本或发布版本。

### 阶段 3：UI 评审

- 增加独立 UI 评审开关和暂停点。
- 保存 Luna 的视觉产物及用户批注。
- 未通过 UI 评审时阻止进入工程实现。

### 阶段 4：Figma 集成

- Luna 创建或更新 Figma 页面、Frame 和组件。
- 平台同步导出图、节点信息和设计 Token。
- 设计版本与代码快照一一关联，并支持视觉对比。

## 九、本期明确不做

- 不删除 `/r/[runId]`、事件 API、事件表或 `foldUpTo`。
- 不实现历史 bundle 存储、版本列表、分支或发布指针。
- 不新增 UI 评审暂停点。
- 不接入 Figma 或其他外部设计工具。
- 不改变现有角色调度、数据库结构和已生成项目数据。

本期只完成可见入口收敛、应用链接替换和方案沉淀，后续按上述阶段独立立项。
