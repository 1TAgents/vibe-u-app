# UI 评审、快照与版本演进方案

> **状态：未来方案，当前不实现。**

当前只保留事件流、历史事件 API、状态折叠和只读回放路由作为技术基础。面向普通用户的“回放 / 重播”入口已经移除，项目卡片改为复制生成应用的公开链接。

## 一、当前能力与未来目标

| 能力 | 当前状态 | 未来目标 |
| --- | --- | --- |
| 需求审核 | 已有开关，默认关闭；可批准或编辑后批准 | 支持退回 Ida 修订、批注和多轮确认 |
| UI 设计 | Luna 输出结构化文字方案 | 产出可视化设计稿和交互原型 |
| UI 评审 | 未实现 | 编码前独立批准设计版本 |
| 应用发布 | 有公开链接和候选/公开存储语义 | 验收后自动发布、可切换历史版本 |
| 历史记录 | 事件流、群聊和内部只读回放 | 正式快照、版本对比和分支 |
| 角色能力 | 同一编排进程中的结构化模型调用 | 独立 subagent 与专业工具 |

当前需求审核的拒绝操作会结束本次运行，不会自动让 Ida 重新修改 PRD。真正的“退回修改”属于后续审核闭环。

## 二、为什么不继续强化回放

团队群聊已经按时间顺序展示角色结论、派单理由、失败证据、测试结果和人工变更。播放式回放与群聊的用户价值重叠，而且容易让人误解为“可以回退到当前帧”。

未来更有价值的是：

1. **需求评审**：确认产品范围和验收边界；
2. **UI 评审**：编码前确认页面构图、视觉语言和交互；
3. **快照与版本**：重新采用旧版本，或从旧状态开始新的开发分支。

事件流不会删除。它继续承担刷新恢复、明确暂停点续跑、故障定位和审计职责，也为未来创建快照提供事件位置。

## 三、目标工作流

```text
用户提出需求
  → Ida 整理 PRD
  → [需求评审，可配置]
  → Luna 产出可视化 UI 方案
  → [UI 评审，可配置]
  → Archie 评估系统结构（需要时）
  → Cody 实现
  → Tess 功能与视觉验收
  → Ida 交付验收
  → 创建稳定快照并发布
```

### 需求评审

未来完整审核应支持：

- 批准当前 PRD；
- 直接编辑后批准；
- 带意见退回 Ida 修订；
- 保存每次修改、批注和结论；
- 只有已批准版本才能成为下游角色的有效输入。

### UI 评审

UI 评审与需求评审独立配置：

- Luna 提交可视化设计产物后暂停；
- 用户可以批准、批注或要求其他方案；
- 未批准的设计不能进入正式实现；
- 纯后端或没有视觉界面的任务可以跳过；
- 纯视觉修改走 Luna → Cody → Tess；涉及系统结构时再经过 Archie。

## 四、版本模型

| 概念 | 含义 |
| --- | --- |
| **Project** | 一个持续演进的产品，包含对话、分支和版本 |
| **Branch** | 从某个快照开始的后续开发路线 |
| **Snapshot** | 某个里程碑上不可变的完整产品状态 |
| **Release** | 当前公开链接指向的稳定快照 |
| **Design Artifact** | 设计文件、Frame、导出图、Token 和交互说明 |

“回退”不应删除或改写历史，而应拆成两个动作：

- **重新发布此版本**：公开链接重新指向已有稳定快照，不调用模型；
- **从此版本继续**：以该快照创建新分支和新聊天上下文，原分支保持不变。

例如 V1 已交付，修改后得到 V2，但用户认为 V1 更好。用户可以直接重新发布 V1，也可以从 V1 创建 V3。V2 仍然保留，便于比较和审计。

代码版本与业务数据必须分开处理。默认只切换代码、设计和配置，不回滚用户数据；发生数据 Schema 变化时，需要先验证兼容性或执行迁移。

## 五、快照内容

快照应保存足够信息，使历史版本不依赖当前构建器重新计算：

- 项目、分支、父快照、事件序号和创建原因；
- 当时有效的 PRD、系统设计、视觉设计和验收标准；
- 完整源码、内容校验值和已编译 JS/CSS bundle；
- QA 计划、执行结果、浏览器结果和已知问题；
- 依赖、构建器和数据 Schema 版本；
- 页面截图、缩略图和视觉差异摘要；
- 外部设计文件、Frame、组件节点和版本引用；
- 提供给后续角色的决策摘要。

只保存事件不够。构建器和依赖升级后，同一份源码可能得到不同产物，因此正式快照必须保存不可变源码和当时的编译结果。

## 六、版本操作

未来版本页面建议提供：

1. **预览**：打开该版本的真实应用；
2. **对比**：比较截图、设计 Token、源码、测试和数据 Schema；
3. **从这里继续**：从快照创建新分支；
4. **设为当前版本**：切换工作区使用的版本；
5. **发布此版本**：更新公开 Release 指针；
6. **命名和备注**：记录“老板确认版”“密度调整前”等业务语义。

## 七、Luna 的专业设计工具

当前 Luna 输出结构化文字设计说明。未来应将 Luna 拆成拥有独立上下文和权限的产品设计 subagent，并接入 Figma 或同类可视化工具。

标准设计产物包括：

- 可评论的设计文件或指定 Frame；
- 桌面端和移动端关键页面；
- 默认、悬停、禁用、错误、空状态和加载状态；
- 颜色、字体、间距、圆角和阴影 Token；
- 页面跳转和关键交互原型；
- PNG/SVG 预览和平台缩略图；
- 设计项与 PRD 验收项的对应关系。

Figma 不应成为唯一事实源。平台仍需保存导出图、结构化 Token、节点引用和设计摘要，避免外部授权失效后历史版本不可识别。

Cody 应消费批准后的设计版本、组件状态和交互说明；Tess 的视觉验收也必须引用同一个设计版本。

## 八、建议数据结构

未来应新增不可变版本表，而不是继续覆盖当前 `app_bundles` 双槽：

```text
project_snapshots
  id
  project_id
  branch_id
  parent_snapshot_id
  event_seq
  kind
  label
  source_files
  compiled_bundle
  prd
  architecture
  design_artifacts
  qa_report
  build_metadata
  created_at

project_branches
  id
  project_id

  head_snapshot_id

  project_id
  snapshot_id
  published_at
```

事件流记录谁在何时创建、批准、切换或发布版本；快照表保存可恢复的物化状态。

## 九、实施顺序

### 阶段 1：补齐稳定发布闭环

- 验收通过时保存并发布当前 bundle；
- 增加 V1 发布、V2 候选、成功晋升和失败保留 V1 的端到端测试；
- 公开应用始终只读取明确发布的版本。

### 阶段 2：版本基础

- 每次成功构建和交付后保存不可变源码与 bundle；
- 增加版本列表、缩略图、预览、命名和备注；
- 将公开应用改为读取正式 Release 指针。

### 阶段 3：恢复与分支

- 支持“从此版本继续”；
- 新分支只继承目标快照之前的有效上下文；
- 支持重新使用或发布历史稳定版本。

### 阶段 4：UI 评审

- 增加独立 UI 评审开关和暂停点；
- 保存视觉产物、用户批注和批准结论；
- 未通过 UI 评审时阻止进入工程实现。

### 阶段 5：设计工具与专业 subagent

- Luna 创建或更新 Figma 页面、Frame 和组件；
- 平台同步导出图、节点信息和设计 Token；
- 设计版本与代码快照关联并支持视觉对比；
- 按角色职责配置独立模型、上下文、工具和权限。

## 十、本期不做

- 不删除 `/r/[runId]`、事件 API、事件表或 `foldUpTo`；
- 不新增快照、分支、版本列表或历史发布指针；
- 不新增 UI 评审暂停点；
- 不接入 Figma 或其他外部设计工具；
- 不把当前角色拆成独立 subagent；
- 不改变既有项目数据。

本期只保留底层能力、收敛普通用户入口并沉淀演进方案，后续按阶段独立实施。
