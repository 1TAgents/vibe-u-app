# 架构设计：六角色四道门

老板提需求，Piper 派活，五个角色干活，四道门判定。
**流程不写死在代码里** —— 下一步谁接，由 Piper 看着当前状态现场决定。

| | |
|---|---|
| 角色 | 6（1 个调度 + 5 个干活） |
| 质量门 | 4 |
| 事件流 | 1 条，唯一真相源 |
| 派单预算 | 20 轮 |

---

## 一、一条公理

> **Agent 产出的是主张，平台产出的是事实。「完成」只能由事实认定。**

下面每一个设计——角色的边界、工具怎么分、门为什么长在那个位置、预算为什么不能由项目经理自己改——全部由这一条推出来。

这条判断来自对 Atoms 的公开实测反馈：*agent 反复声称任务已完成，而预览面板里的代码根本跑不起来*。所以这个系统里所有「完成」都必须落到可检验的东西上。

---

## 二、主循环

```
                    老板
                     │  一句话需求 / 中途改主意
                     ▼
          ┌──────────────────────────┐
          │  Piper · 项目经理        │ ◀──────────┐
          │  不干活，只决定派给谁    │            │
          │  输出受 schema 约束      │            │
          └────────────┬─────────────┘            │
                       │ next + brief             │
                       ▼                          │
          ┌──────────────────────────┐            │
          │  五个角色干活            │            │  事实回流
          │  Ida 产品 / Luna 设计    │            │
          │  Archie 架构 / Cody 实现 │            │
          │  Tess 质量               │            │
          └────────────┬─────────────┘            │
                       │ 产物                      │
                       ▼                          │
          ┌──────────────────────────┐            │
          │  门 · 由产物触发         │────────────┘
          │  平台独占，无 LLM        │
          └──────────────────────────┘
```

Piper 每轮都基于**最新事实**重新决策。所以它不需要预先知道完整流程，只需要知道「现在到哪儿了、刚发生了什么」。

### 调度器的输出契约

```jsonc
{
  "next":   "pm | designer | architect | engineer | qa | accept | ask_human | done",
  "reason": "为什么是他",        // 必须进事件流，否则调度本身成了新黑盒
  "brief":  "给他的任务简报"      // 他这一轮具体干什么
}
```

## 三、六个角色

| 角色 | 决定什么 | 产出 |
|---|---|---|
| **Piper** 项目 | 谁来做、卡在哪了、要不要找人 | 派单决策 · **不产出主张** |
| **Ida** 产品 | 做什么、优先级、能不能交付 | PRD · 验收结论 |
| **Luna** 设计 | 长什么样、给谁用 | 配色 · 字阶 · 密度 |
| **Archie** 架构 | 数据怎么组织、页面怎么分 | collection 模型 · 页面结构 |
| **Cody** 实现 | 代码怎么写 | React 源码 · 修复 |
| **Tess** 质量 | 怎么验、验什么 | 验收用例 |

**产品经理和项目经理是两个人。** Ida 决定「做什么」，Piper 决定「谁来做」。

原先塞给 Ida 的质量归因（这个 bug 该谁修）本来就不是产品的活，现在归位了。

---

## 四、四道门 = 触发式 hooks

流程一旦不固定，「第 N 步之后跑门」这个位置就不存在了。所以门改成挂在**产出了什么**上——本质就是 hook。

### 注册表

| 触发于 | 门 | 产出的事实 | 阻塞 |
|---|---|---|---|
| `artifact:files` | 构建门 | 能不能编译 | 是 |
| `artifact:files` | 静态审计 | 有没有注定出问题的写法 | 是 |
| `state:code-ready` | 界面探查 | 三层真实控件名 | 否 · 只采信息 |
| `artifact:tests` | 覆盖门 / target 门 | 测试计划自身合不合格 | 否 · 只警告 |
| `tests:ready` | 功能验收 | 用例逐条过没过 | 是 |
| `state:qa-passed` | 交付验收 | 色板 · DOM 结构 · 客观缺陷 | 是 |

`blocking: false` 那两行是刻意的：

- **界面探查不是门** —— 它不判定，只采信息喂给 Tess
- **覆盖门降级为警告** —— 它自己也可能判错，不该枪毙整场生成（见第八节）

### 和普通 hook 的三点不同

1. **不能被跳过** —— subagent 无权关它，Piper 也无权关它。注册表是平台侧静态配置。
2. **有返回值，且进状态** —— 门不只是拦一下，它产出事实：测试报告喂给 Piper，采证喂给 Ida。它是「产物 → 事实」的转换器。
3. **由产物触发，不由位置触发** —— 只要出现新代码，构建门和审计门必然跑，不管此刻流程走到哪。

> **Piper 决定谁来干活，门决定干完了算不算数。两者都不能碰对方的地盘。**

## 五、三次真实决策

### 测试挂了 3 条，交给谁？

Piper 拿到测试报告与失败证据（第几步、期望什么、实际什么），判断这属于哪一层：

```jsonc
{ "next": "architect",
  "reason": "失败集中在跨页签的数据传递，模型里没有承载这个关系的字段",
  "brief": "补上 note 与 book 的关联字段" }
```

### 有预览版了，老板又提新需求，交给谁？

看影响面：

| 老板说 | 派给 | 为什么 |
|---|---|---|
| 把主色换成暖色调 | `designer` | 只动视觉 |
| 加一个按月筛选 | `pm` | PRD 要先动 |
| 记录要能分享给别人 | `architect` | 数据模型要动 |

### 那正常流程还在吗？

在，但形态变了——从「代码里写死的顺序」变成 **Piper 的先验知识**：

> 常见路径是 需求 → 设计 → 架构 → 实现 → 测试 → 验收。没有特殊情况就照走。

规则从代码搬进了提示词，但仍然存在。

## 六、预算：动态调度唯一的真风险

来回踢皮球、烧钱不收敛，是这类架构最容易死的地方。所以 Piper 还管预算——真实 PM 本来就管这个。

### 预算分两级

| 级别 | 内容 | 归谁 |
|---|---|---|
| 局部 | 解析重试、构建自愈 | 留在原地，属于「一次干活内部」 |
| 全局 | 派单轮次、同角色连派、同签名复现、token | 上交 Piper |

判断标准：**跨角色的重试归 PM，一次干活内部的重试留在原地。**

### 全局预算

| 维度 | 上限 | 说明 |
|---|---|---|
| 派单轮次 | 20 | 一级控制。方差小、语义清楚 |
| 同角色连派 | 3 | 连着派同一个人三次还没好，换人或找人 |
| 同签名复现 | 3 | 同一个失败原样出现三次，停止自动派单 |
| token / 成本 | 只记录 | 方差太大（架构设计和改文案差十倍），前期不设硬线 |

### 三条规则

**① 平台硬性执行，Piper 看得见但改不了。**
和门同一条原则：Piper 的职责是把预算花好，不是决定有多少预算。

**② 要让它看见余额，因为余额会改变决策。**

```
剩 15 轮 →  「先让 Archie 改数据模型，再让 Cody 跟着调」（可以试探）
剩 2 轮  →  「不试了，把当前问题整理清楚交给人」（必须收敛）
```

**③ 耗尽时交付当前最好的版本，不是报「运行失败」。**
如果已经有能跑的产物，就交出去，附上「哪两条没过、卡在哪、试过什么」。老板宁可拿到一个有已知问题的东西。

### 数据结构

```jsonc
budget: {
  dispatches: { used: 4, max: 20 },
  sameRole:   { role: "engineer", streak: 2, max: 3 },
  signatures: { "qa:第7步找不到…": 2, max: 3 },
  tokens:     { used: 61067 },      // 只记录
  costUsd:    { used: 0.0092 }      // 只记录
}
```

每次派单时随状态一起给 Piper 看，每次变化都进事件流——所以回放时能看到「它是在还剩 2 轮的时候决定放弃修复、转人的」。

## 七、分层

| 层 | 内容 | 本次改动 |
|---|---|---|
| L4 界面 | 群聊 · 回放 · 项目列表 | 多一个 Piper 在群里发言 |
| L3 编排 | 调度循环 · 门注册表 · 预算 | **重写** |
| L2 角色 | prompt + schema + 只读工具 | 加输入契约与工具集 |
| L1 判定 | builder · testrunner · delivery · audit | **零改动** |
| L0 事件流 | events · fold · store | 加 `dispatch.decided` |

### 关键性质：L1 不依赖 L2

七个判定模块零 LLM 依赖，已验证：

```
builder.ts  testrunner.ts  delivery.ts  timer-safety.ts
stressCoverage.ts  targetGate.ts  appdata.ts
```

判定服务根本不知道 agent 存在，它只接受一堆文件、产出一组事实。这带来三件事：

- 能脱离 LLM 单测（现有 200+ 条断言）
- 换模型、换角色、改提示词，判定标准一动不动
- **它没法被说服** —— 这是「不信自我汇报」唯一能落地的地方

也正因如此，这次重构不碰系统里最难写、也最值钱的那部分。

## 八、工具怎么分

| 给 subagent | 留在平台 |
|---|---|
| 读源码、查历史失败、探界面、翻事件流 | 跑构建、跑测试、采证、标记通过 |

**理由**：给 Cody 一个 `build` 工具，「构建通过」就变成他的主张，四道门立刻降级成四条自述——正是这个项目要解决的那个问题。

顺带说明现状：界面探查目前是平台代 Tess 执行、结果预注入她的 prompt。改成她自己能调的只读工具，她就能主动探她关心的那部分（比如「我要测筛选，先点开『已完成』页签看看里面有什么」）。

## 九、事件流

上面每一步——每个 token、每次重试、每道门的判定、每次派单决策——都作为事件追加进同一条流。

```
                  ┌──────────────────┐
                  │ 事件流 · 唯一真相源 │
                  └────────┬─────────┘
                           │  同一个 fold 函数
          ┌────────────────┼────────────────┐
          ▼                ▼                ▼
      实时看进度        逐帧回放         服务端续跑
      (群聊界面)      (分享给别人)     (下一阶段从这恢复)
```

**一份实现，三个消费者。** 所以「你看到的」和「分享出去别人看到的」不可能不一致——这是结构保证，不是纪律保证。回放页里没有一行回放专用的渲染代码。

它还顺带解决两个工程问题：每阶段**无进程内存依赖**（状态靠 fold 恢复），所以任意中断能续上、Serverless 能跑；并发跑 N 条生成也不需要任何新后端设施。

### 界面：一个群

可观测 ≠ 把所有东西摊开。早期版本把每个节点的完整产物铺在时间轴上，信息量大到没人看。

现在是**群聊**：每条消息只说结论，点进去才展开那个人这一步真正干的活。Piper 也照这个规则——

```
群里显示   Piper：3 条用例失败，是数据模型的问题 → Archie

点开才看   · 失败证据：第 7 步找不到「张三 查看」…
          · 判断依据：失败集中在跨页签数据传递
          · 候选与排除：为什么不是 Cody
          · 本轮预算：第 4 次派单 / 上限 20
```

它的决策是整个系统里信息量最高的一句话——**为什么这个 bug 给了架构师而不是工程师**——所以必须可见，不能藏在后台。

## 十、已知边界

### jsdom 没有布局引擎

滚动、像素、真实排版测不到。「点了导航没反应」这类缺陷在功能验收里**结构性看不见**——因为所有区块都在 DOM 里，点完导航后任何文字断言都会空洞地通过。

目前靠静态审计接住个别规则，这是补丁不是解法。真正的解法是判定层加一个真实浏览器档位，只在交付验收前跑一次。

### 生成物依附平台

HTML 由平台路由现场拼出、数据走平台的 `/api/appdata`。交付的是一个能用、能分享的链接，**不是客户自己拥有的产品**。

瓶颈在注入的 `db` 契约写死了后端地址。本期明确不做。

### 动态调度会降低可复现性

同一个需求两次跑，过程可能不同。缓解手段是把每次派单的 `next` 与 `reason` 写进事件流、回放严格按记录走、不重新调模型。

但「两次跑出一样的过程」这个性质确实换掉了 —— 换来的是能处理真实情况（bug 给谁、中途改需求给谁）。**这是个真实的取舍，不是免费的。**

### 门自己也可能判错

跑 20 场景批次时反复出现：每次去查「门连拒两轮」的现场，结论都是门判错了，不是被拦的东西真有问题。

而代价完全不对称——门判错会让整场生成作废且**没有任何失败证据**；被拦的东西真有问题，代价只是这轮验证弱一点。

所以测试计划类的门（覆盖门、target 门）修订次数用尽后只记录、不终止。
