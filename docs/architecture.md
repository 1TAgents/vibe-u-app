# 架构设计：六个角色与五道质量门

VibeU 把一句需求交给一支 AI 产品团队，并由平台证据决定结果是否真的可交付。

> **角色可以提出“完成”，但只有平台证据能够确认“完成”。**

当前架构由四部分组成：动态调度、结构化角色产物、平台质量门和追加式事件流。

## 一、整体流程

```text
用户需求或中途变更
        ↓
Piper 根据最新事实派单
        ↓
Ida / Luna / Archie / Cody / Tess 产出结构化结果
        ↓
平台按产物触发构建、审计、测试与交付采证
        ↓
事实写入事件流，再交给 Piper 判断下一步
```

常见路径仍然是：

```text
需求 → 视觉设计 → 系统结构 → 工程实现 → 功能验收 → 交付验收
```

这条路径是 Piper 的默认先验，不是写死的状态机。中途需求变更或质量失败发生后，Piper 会根据最新产物、失败证据和预算重新选择角色。

调度输出受 schema 约束：

```jsonc
{
  "next": "pm | designer | architect | engineer | qa | accept | ask_human | done",
  "reason": "为什么交给这个角色",
  "brief": "本轮需要完成的具体任务"
}
```

`reason` 和 `brief` 都会进入事件流，用户可以看到任务为什么交给架构师而不是工程师。

## 二、六个角色

| 角色 | 职责 | 主要产物 |
| --- | --- | --- |
| **Piper · 项目经理** | 判断下一步交给谁、何时收敛或交给人 | 派单角色、理由和任务简报 |
| **Ida · 产品负责人** | 定义产品范围并完成最终交付验收 | PRD、交付结论 |
| **Luna · 产品设计师** | 定义视觉语言、页面构图和关键状态 | 结构化视觉方案 |
| **Archie · 系统架构师** | 定义数据模型、页面结构和系统边界 | collection 模型、页面方案 |
| **Cody · 全栈工程师** | 实现新功能并修复代码缺陷 | React 源码 |
| **Tess · 质量工程师** | 根据 PRD 和真实界面编写验收用例 | 结构化测试计划 |

Piper 只调度，不编写 PRD、设计或代码。Ida 决定“做什么”，Piper 决定“下一步由谁做”。

当前六个角色由独立提示词、输入契约和输出 schema 实现，仍属于同一编排进程中的模型调用，并不是拥有独立运行环境和专业工具的 subagent。角色工具化方案见 [UI 评审、快照与版本演进方案](versioning-and-design-review.md)。

## 三、五道质量门

质量门由平台静态注册，角色和 Piper 都不能关闭。实际注册表位于 `src/lib/gates.ts`。

| 触发条件 | 质量门 | 作用 | 阻塞 |
| --- | --- | --- | --- |
| `artifact:files` | 构建门 | 使用真实构建器验证源码能否编译 | 是 |
| `artifact:files` | 静态审计 | 检查计时器生命周期等高风险写法 | 是 |
| `artifact:tests` | 测试计划体检 | 检查场景覆盖和操作目标是否可信 | 否，只记录警告 |
| `state:code-ready` | 功能验收 | 在 jsdom 中执行逐步操作与断言 | 是 |
| `state:qa-passed` | 交付采证 | 从构建产物提取色板、DOM、可访问性和客观缺陷 | 是 |

界面探查不是质量门。代码构建通过后，平台会额外渲染页面，采集首屏、打开表单和创建记录后的真实控件名，再把结果提供给 Tess，减少测试计划凭空猜测控件名称。

测试计划体检采用非阻塞策略：它可以指出覆盖不足或目标可疑，但不会因为启发式判断失误直接让整次生成失败。真正的功能验收仍然是阻塞门。

## 四、动态调度与收敛

Piper 每轮看到的是已经发生的事实：现有产物、构建结果、失败步骤、交付证据、历史变更和剩余预算。它无法修改质量门和预算上限。

平台当前执行三类全局限制：

| 限制 | 上限 | 作用 |
| --- | --- | --- |
| 总派单轮数 | 50 | 给多角色协作、复核与修复留出空间，同时防止流程无限运行 |
| 同角色连续派单 | 3 | 防止同一角色反复尝试相同方向 |
| 同一失败签名 | 3 | 防止修复没有生效却继续消耗模型 |

Token 和成本会被记录并展示，但目前不作为硬性终止条件。结构化结果的解析重试属于单次角色调用内部预算，不占用全局派单轮次。

预算耗尽或 Piper 主动请求人工介入时，平台会记录当前产物、失败证据和尝试历史。当前实现只有完整满足交付条件的运行才标记成功；未验收的候选产物不会作为新的公开版本发布。

## 五、事件流与可观测性

以下内容都会作为事件追加保存：

- 用户需求与后续变更；
- Piper 的派单角色、理由和任务简报；
- 角色输入、原始输出、结构化产物与解析重试；
- 模型用量、成本、网络重试和推理模式降级；
- 构建、静态审计、界面探查、测试和交付采证结果；
- 需求审核、人工终止和最终状态。

`foldEvents` 使用同一组事件恢复工作区状态，并投影为团队群聊、设计、代码、预览和测试视图。事件流是**协作运行状态**的事实来源；应用 bundle、运行索引和生成应用的业务数据由独立存储结构保存。

当前事件流已经支持：

- 刷新后恢复工作区和群聊记录；
- 从需求审核等明确暂停点继续运行；
- 保留只读回放路由，供内部审计和未来版本能力复用；
- 在后续需求变更时恢复已有产物并重新调度。

任意进程中断后的自动断点续跑尚未实现。连接取消或运行异常会进入明确的 `aborted` 或 `failed` 终态，而不是静默停留在运行中。

## 六、生成应用运行时

### 公开应用

生成应用通过 `/a/[runId]` 以普通 HTML 页面打开，不包含 VibeU 工作区外壳。构建后的 JavaScript 和 Tailwind CSS 被内联到页面中，应用不依赖浏览器端临时编译器。

存储层区分两类 bundle：

- `candidate`：供工作区预览和验证使用；
- `published`：公开应用链接读取的稳定版本。

文件存储和 Postgres 适配器都实现了候选保存、公开读取和原子晋升语义。不过，验收成功后自动晋升候选版本的主流程仍需要补齐端到端闭环与回归测试；在此之前，不把它描述为完整的版本发布系统。

### 应用数据

平台为生成代码注入统一的 `db` 接口，提供查询、新增、更新和删除能力。模型不需要为每个应用重新设计后端协议。

数据按 `runId + collection` 隔离：

- 本地默认写入 `.data/` 下的 JSON/JSONL 文件；
- 设置 `DATABASE_URL` 后使用 Postgres/Neon；
- 功能验收按测试套件和用例创建独立数据空间；
- 界面探查使用一次性命名空间，不污染公开应用数据。

运行事件、应用 bundle 和应用业务数据分别存储。当前数据隔离单位是项目运行，不是最终用户或租户。

## 七、分层与责任边界

| 层 | 主要模块 | 责任 |
| --- | --- | --- |
| 界面层 | `app/`、`components/` | 首页、工作区、群聊、预览和测试展示 |
| 编排层 | `orchestrator.ts`、`piper.ts`、`budget.ts` | 动态调度、预算和人工交接 |
| 角色层 | `roles.ts`、`contracts.ts`、`agent-call.ts` | 提示词、输入输出契约和模型调用 |
| 判定层 | `gates.ts`、`builder.ts`、`testrunner.ts`、`delivery.ts` | 构建、审计、功能测试和交付证据 |
| 状态层 | `events.ts`、`fold.ts`、`store.ts` | 事件定义、状态恢复和持久化 |

判定层不依赖角色的自我汇报。替换模型、角色提示词或未来 subagent 工具时，平台质量标准可以保持不变。

## 八、当前边界

- **没有真实浏览器布局引擎**：功能验收基于 jsdom，不能覆盖像素级布局、真实滚动和视觉回归。
- **生成应用仍依附平台**：公开页面和数据接口由 VibeU 服务提供，还不是独立域名、独立运行环境和独立数据源。
- **不是完整版本系统**：目前只有候选/公开双槽存储，没有快照列表、分支、版本比较和历史发布指针。
- **不是多租户产品**：暂未实现最终用户登录、租户权限和按终端用户隔离的数据空间。
- **动态调度存在方差**：相同需求的两次运行可能经过不同角色路径，事件流只能记录过程，不能保证过程完全可复现。
- **质量门并非绝对正确**：测试计划类判断因此保持非阻塞，真实浏览器验证仍是后续重点。

未来的 UI 评审、快照、版本分支、专业 subagent 和设计工具接入见 [UI 评审、快照与版本演进方案](versioning-and-design-review.md)。
